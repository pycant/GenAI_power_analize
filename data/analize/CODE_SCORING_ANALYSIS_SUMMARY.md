# 代码任务打分逻辑分析总结

**日期**: 2026-03-04  
**分析对象**: 60个代码生成样本，12个模型  
**状态**: 分析完成 ✅

---

## 📊 核心发现

### 1. 编译成功 ≠ 功能正确（最重要的发现）

```
平均编译成功率: 50.0%
平均测试通过率: 33.3%
差距: 16.7个百分点

编译成功但测试全失败的样本: 20个 (33.3%)
```

**结论**: 当前评分体系过度依赖编译成功率（60%权重），但编译成功不代表代码功能正确。

### 2. 模型表现差异巨大

| 模型 | 编译率 | 测试通过率 | 差距 | 评价 |
|------|--------|-----------|------|------|
| gemma_4b_ol_q4km | 100% | 80% | +20% | 🏆 最佳 |
| deepseek_8b_ol_q4km | 60% | 67% | -7% | ✅ 优秀（测试率高于编译率） |
| qwen25_7b_hf_4bit | 60% | 67% | -7% | ✅ 优秀 |
| gemma_2b_hf_4bit | 80% | 0% | +80% | ❌ 最差（编译成功但测试全失败） |
| qwen25_3b_hf_4bit | 80% | 0% | +80% | ❌ 最差 |

**关键洞察**: 
- deepseek_8b 虽然编译率只有60%，但测试通过率达67%，说明它生成的代码质量更高
- gemma_2b 和 qwen25_3b 编译率80%，但测试通过率0%，说明代码语法正确但逻辑错误

### 3. 代码长度和复杂度的"合理范围"不合理

**当前假设**:
- 代码长度: 10-50行为"合理"
- 复杂度: 1-10为"合理"

**实际数据**:
- 65%的样本不在假设的"合理范围"内
- 代码长度 P25-P75: 2-12行（远小于假设的10-50）
- 复杂度 P25-P75: 1-7（接近假设但仍有偏差）

**结论**: 不应该用主观假设的"合理范围"，应该基于实际数据分布。

### 4. 代码长度与测试通过率的关系

| 长度分组 | 测试通过率 | 编译率 | 平均复杂度 |
|---------|-----------|--------|-----------|
| 很短(≤5行) | 6.2% | 53.3% | 2.0 |
| 短(6-15行) | 75.0% | 22.2% | 6.0 |
| 中(16-50行) | 60.0% | 83.3% | 10.4 |

**洞察**: 
- 6-15行的代码测试通过率最高（75%）
- 很短的代码（≤5行）虽然编译率高，但测试通过率很低
- 说明代码长度和质量不是简单的线性关系

## ⚠️ 当前评分体系的3大问题

### 问题1: 权重设置不合理（严重程度: HIGH）

**当前**: 编译60% + 长度20% + 复杂度20%

**问题**:
1. 编译成功率权重过高，但它不能反映功能正确性
2. 长度和复杂度权重相同，但它们的重要性不同
3. 完全忽略了测试通过率（最重要的指标）

**影响**: 33.3%的样本（20个）被高估

### 问题2: "合理范围"假设错误（严重程度: MEDIUM）

**当前**: 假设10-50行、复杂度1-10为"合理"

**问题**:
1. 65%的样本不在假设范围内
2. 不同题目的合理范围差异很大
3. 简单题目（如multiply）只需1行，复杂题目可能需要50+行

**影响**: 39个样本（65%）的评分被扭曲

### 问题3: 缺少关键指标（严重程度: HIGH）

**当前缺失**:
- 测试通过率（最重要）
- 时间复杂度
- 空间复杂度
- 代码可读性
- 边界用例处理

## 💡 改进建议（3个方案）

### 方案A: 功能优先评分（推荐用于生产环境）

```python
# 分层评估
if test_pass_rate == 0:
    base_score = 0.2  # 测试全失败
elif test_pass_rate < 0.5:
    base_score = 0.4 + 0.2 * test_pass_rate  # 部分通过
elif test_pass_rate < 1.0:
    base_score = 0.6 + 0.3 * test_pass_rate  # 大部分通过
else:
    base_score = 0.9  # 全部通过

# 质量加分（最多+10%）
quality_bonus = 0.1 * (
    0.4 * simplicity_score +
    0.3 * efficiency_score +
    0.3 * readability_score
)

final_score = min(1.0, base_score + quality_bonus)
```

**权重分配**:
- 测试通过率: 90%（基础分）
- 代码质量: 10%（加分项）

**优点**:
- 功能正确性优先
- 避免编译成功但逻辑错误的代码得高分
- 质量作为加分项，不会主导评分

### 方案B: 多维度独立评分（推荐用于研究分析）

```python
scores = {
    # 功能维度
    'functional_correctness': test_pass_rate,
    'compilation_success': compilation_rate,
    
    # 效率维度
    'time_complexity': time_complexity_score,
    'space_complexity': space_complexity_score,
    
    # 质量维度
    'code_simplicity': simplicity_score,
    'code_readability': readability_score,
    
    # 鲁棒性维度
    'edge_case_handling': edge_case_score,
}
```

**优点**:
- 保留完整信息
- 不同场景可以选择不同维度
- 避免主观权重设置
- 便于多角度分析

### 方案C: 动态权重评分（推荐用于灵活场景）

```python
# 根据任务类型动态调整权重
if task_type == 'algorithm':
    weights = {
        'functional': 0.5,
        'efficiency': 0.3,
        'quality': 0.2
    }
elif task_type == 'simple_function':
    weights = {
        'functional': 0.7,
        'efficiency': 0.1,
        'quality': 0.2
    }
elif task_type == 'complex_system':
    weights = {
        'functional': 0.4,
        'efficiency': 0.2,
        'quality': 0.4
    }
```

**优点**:
- 适应不同任务类型
- 更灵活
- 可以根据实际需求调整
